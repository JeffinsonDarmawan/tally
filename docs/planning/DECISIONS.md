# Architecture Decision Records (ADRs)

Lightweight log of decisions that shape the project, with the *why* so future-us doesn't
relitigate them. Newest on top. Each entry: context → decision → consequences.

Format inspired by [Michael Nygard's ADRs](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions).

---

## ADR-0006 — No third-party tooling attribution in history
**Status:** Accepted · 2026-05-30
**Context:** The owner wants the repository to read as a first-party project with a clean,
owner-authored history.
**Decision:** Commits and PRs are authored solely by the repository owner. No co-author trailers,
no "generated by" footers, and no AI/agent config files are committed (they're gitignored).
**Consequences:** Default tooling attribution is suppressed. Contributors must keep commit
metadata clean.

## ADR-0005 — Isolated, reproducible development environment
**Status:** Accepted · 2026-05-30
**Context:** Work should happen in a consistent environment so dependencies don't leak into the
global system and every machine builds identically.
**Decision:** Use the lightweight standard for this stack: pin the Node version via `.nvmrc` /
`.node-version` (Node **24 LTS**, matching Vercel's runtime), keep dependencies project-local in
`node_modules`, and keep secrets in a gitignored `.env` seeded from `.env.example`. No Docker is
required. A Dev Container can be layered on later if stronger isolation is wanted (see
[`../ENVIRONMENT.md`](../ENVIRONMENT.md)). Chosen over a Dev Container because it needs no Docker,
works with the Node already installed, and is enough for solo/small-team work.
**Consequences:** Reproducible builds; onboarding is `nvm use → npm install → cp .env.example .env`.
A `package-lock.json` (Phase 0) will lock exact versions.

## ADR-0004 — Public GitHub repository named `tally`
**Status:** Accepted · 2026-05-30
**Context:** The app is private-use (5 friends) but the source can be open.
**Decision:** Host on GitHub as a **public** repo named `tally`. No secrets are committed; RLS and
gitignored `.env` keep data and credentials safe.
**Consequences:** Source is publicly visible; we must remain disciplined about never committing
secrets. The anon Supabase key is safe to expose by design (RLS enforces access).

## ADR-0003 — Defer the Vite scaffold to Phase 0
**Status:** Accepted · 2026-05-30
**Context:** The brief mandates a phased build with review checkpoints. The foundation pass is
about VCS + docs + architecture, not app code.
**Decision:** Establish repository, docs, and the *planned* `src/` layout now; create the actual
Vite app in Phase 0 so it gets its own review.
**Consequences:** The repo has no runnable app yet; `README` setup steps activate after Phase 0.

## ADR-0002 — Feature-sliced (feature-based) source architecture
**Status:** Accepted · 2026-05-30
**Context:** The app has several distinct domains (auth, expenses, dashboard, settle-up,
recurring, summary, history, activity, notifications) plus shared UI and a critical pure balance
engine.
**Decision:** Organize `src/` **by feature/domain**, not by file type. Each feature owns its
components, hooks, API calls, and types and exposes a small public surface via `index.ts`. Truly
shared UI, libraries, and utilities live in dedicated top-level folders. See
[`../architecture/FILE_ORGANIZATION.md`](../architecture/FILE_ORGANIZATION.md).
**Consequences:** Features are self-contained and deletable; co-location keeps related code
together. References: bulletproof-react, Feature-Sliced Design.

## ADR-0001 — `expense_shares` is the single source of truth for "who owes what"
**Status:** Accepted (from the brief) · 2026-05-30
**Context:** Five split methods must reconcile to one canonical ledger; the balance engine should
never re-derive splits.
**Decision:** Whatever the split method, saving an expense computes and persists one
`expense_shares` row per involved user, with `SUM(amount) == total_amount`. The paying side lives
in `expense_payers`. The engine only sums these rows (see `PROJECT_BRIEF.md` §5–§6).
**Consequences:** The engine stays simple and testable; correctness hinges on the save path
writing exact, reconciled shares (the cent-distribution helper must be unit-tested).
